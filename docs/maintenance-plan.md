## Scope and Verification

- Changelog dates determine discovery and sequence, not a historical target. Compare every touched endpoint/channel's complete contract with its current official documentation, including request, response, behavior, and rate limits.
- If a later date revisits an already synchronized contract, verify it without adding duplicate changes. Record conflicts between announcements, tables, and examples explicitly.
- Keep changes minimal and preserve user edits. Each development turn ends with targeted verification and an explanatory local commit; no push.
- Use deterministic fixtures/local servers for trading contracts. Do not place live orders, automatically activate account features, or treat local tests as proof of production behavior.
- After 4-5 development turns, review preceding changes against documentation and revise upcoming scope/order before continuing.

## Review Remediation — 2026-10-01

- R1: removed the unidentified generic-error trading-query fallback and restricted login replies to login request types. Current id+op command matching, numeric/per-item outcomes, and raw envelopes remain unchanged. Missing/unrelated order responses remain uncertain rather than being replaced by a subscription error.
- R2: every subscribe send uses an echoed correlation ID, generated when absent without mutating the stored request; explicit caller IDs are preserved and must be unique according to the official contract. Missing/foreign IDs and wrong operations do not complete the wait. Known correlated failures retain numeric codes when available and raw JSON, including optional/missing code/message fields without fabricated numeric codes.
- R3: all distinct requested arguments must be acknowledged, in any order, before Success/Confirmed. Duplicate ACKs do not advance other arguments. State is local to each send attempt, protected during callback dispatch, and closed after completion/timeout so SDK-retained late handlers cannot consume a later attempt. Existing SDK reconnect calls receive fresh state and generated IDs. Successful intermediate ACKs use a debug-only generic handler rather than false unhandled-message warnings; it never confirms a request or absorbs error events.
- The protected unsubscribe helper uses the same all-argument completion rule. Only orders-only unsubscribe requests add IDs: the complete orders channel explicitly documents them for both operations, while the [general unsubscribe table](https://www.okx.com/docs-v5/en/#overview-websocket-unsubscribe) omits them. Other channels retain their existing ID-less wire contract and exact argument matching; unidentified errors are not guessed into a request result. The final review below records that the SDK public cleanup path discards this helper's result.
- Related boundary discovery: preserving login behavior reproduced two pre-existing failures: documented event:error/60009 was ignored and event:login rejection dereferenced a null deserialization error. Authentication now returns the decoded numeric error/raw response and resets its authentication flag. Only the [documented authentication-specific WS codes](https://www.okx.com/docs-v5/en/#error-code-websocket-public-general-class) without subscription identity are recognized during authentication; ambiguous generic request/subscription errors are not attributed by message text.

Verification: the original seven review cases and actual send/wait scenarios became permanent regressions; 10 initial acknowledgement cases and the two login cases failed before their fixes. All 55 new safety cases and all 699 offline tests pass; both netstandard targets build with zero warnings/errors. Coverage includes concurrent identical filters, ordered/reversed/duplicate ACKs, partial failure, missing/malformed identity, optional error fields, raw outcomes, request immutability/root ID serialization, repeated subscription attempts, completed/timed-out subscription callbacks, protected-helper multi-argument unsubscribe, authentication codes, and unchanged generic channel routing. An older orders-unsubscribe fixture now echoes the sent ID, as the current contract requires. No live orders, credentials from the environment, private network connections, or server-enforcement tests were used.

Boundaries: a timeout or partial failure does not prove that zero server-side subscriptions exist; failed local subscription cleanup and existing reconnect behavior remain SDK-owned. No compensating unsubscribe, new automatic reconnect/resubscription, or trading retry was added. For non-orders ID-less unsubscribe, concurrent identical filters cannot be distinguished by ID; do not claim otherwise. Reconcile uncertain trading/subscription state deliberately. The follow-up was implemented without changing 5.6.820 metadata and is now included in the 5.6.826 source/package build; previously built/installed 5.6.820 packages are not evidence of these fixes. Immediate documentation correction: the late-handler protection claim applies to subscription/unsubscription waits, not authentication. Complete unsubscribe acknowledgement is a protected-helper guarantee, not a guarantee of the SDK public local-close APIs. Do not use `IsAuthendicated` after an uncertain/expired attempt as proof of current connection readiness, or public unsubscribe completion/true as proof of remote removal. Reconcile uncertain state explicitly; no trading replay is justified by either signal.
