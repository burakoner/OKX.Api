## Scope and Verification

- Changelog dates determine discovery and sequence, not a historical target. Compare every touched endpoint/channel's complete contract with its current official documentation, including request, response, behavior, and rate limits.
- If a later date revisits an already synchronized contract, verify it without adding duplicate changes. Record conflicts between announcements, tables, and examples explicitly.
- Keep changes minimal and preserve user edits. Each development turn ends with targeted verification and an explanatory local commit; no push.
- Use deterministic fixtures/local servers for trading contracts. Do not place live orders, automatically activate account features, or treat local tests as proof of production behavior.
- After 4-5 development turns, review preceding changes against documentation and revise upcoming scope/order before continuing.

| Finding | Evidence and impact | Proposed corrective scope |
| --- | --- | --- |
| R1 — P1: generic subscription error completes an unrelated trading query | `OkxBaseSocketClient.HandleQueryResponse` accepts any `event:error` with code/msg after the id+op branch, without matching request kind or ID. Four probes (Place/Amend, foreign subscription ID or no ID) incorrectly return handled=true for code 60012. A subscription rejection on the same connection can therefore be reported as the trading command's failure while the actual order outcome remains unknown; blind retry can duplicate an accepted placement. | Isolate generic errors by the documented request kind/identity; never attribute an unidentified subscription error to a trading command. Preserve legitimate login/command error handling, numeric/raw outcomes, and no automatic retry. |
| R2 — P2: subscription replies ignore supplied IDs | `HandleSubscriptionResponse` accepts any error before checking the request, and successful replies compare only arg. Two probes with request ID SubscriptionA and response ID SubscriptionB incorrectly complete A (subscribe/error). High-level helpers currently omit IDs, but the underlying request model supports them; adding envelope ID fields did not implement correlation. | Match IDs when supplied and use request-scoped subscription identity. Define safe ID-less behavior rather than guessing from error-message text; check subscribe/unsubscribe and shared-channel compatibility. |
| R3 — P1: first argument ACK completes a multi-argument subscription | The orders IEnumerable overload sends SPOT and OPTION args as one request/subscription. A SPOT-only acknowledgement immediately returns handled=true/Success=true; the remaining OPTION confirmation or later rejection is not awaited by that completed request. One probe reproduces this. Consumers can believe all order filters are active although some were never confirmed, on a channel with no initial snapshot. | Await every requested argument before reporting whole-request success and propagate correlated failure. Cover duplicate/out-of-order ACKs, missing/late rejection, timeout, and fresh acknowledgement state on reconnect; preserve callback/API shape and exact ACK argument matching. |

## Review Remediation — 2026-10-01

- R1: removed the unidentified generic-error trading-query fallback and restricted login replies to login request types. Current id+op command matching, numeric/per-item outcomes, and raw envelopes remain unchanged. Missing/unrelated order responses remain uncertain rather than being replaced by a subscription error.
- R2: every subscribe send uses an echoed correlation ID, generated when absent without mutating the stored request; explicit caller IDs are preserved and must be unique according to the official contract. Missing/foreign IDs and wrong operations do not complete the wait. Known correlated failures retain numeric codes when available and raw JSON, including optional/missing code/message fields without fabricated numeric codes.
- R3: all distinct requested arguments must be acknowledged, in any order, before Success/Confirmed. Duplicate ACKs do not advance other arguments. State is local to each send attempt, protected during callback dispatch, and closed after completion/timeout so SDK-retained late handlers cannot consume a later attempt. Existing SDK reconnect calls receive fresh state and generated IDs. Successful intermediate ACKs use a debug-only generic handler rather than false unhandled-message warnings; it never confirms a request or absorbs error events.
- Unsubscribe uses the same all-argument completion rule. Only orders-only unsubscribe requests add IDs: the complete orders channel explicitly documents them for both operations, while the [general unsubscribe table](https://www.okx.com/docs-v5/en/#overview-websocket-unsubscribe) omits them. Other channels retain their existing ID-less wire contract and exact argument matching; unidentified errors are not guessed into a request result.
- Related boundary discovery: preserving login behavior reproduced two pre-existing failures: documented event:error/60009 was ignored and event:login rejection dereferenced a null deserialization error. Authentication now returns the decoded numeric error/raw response and resets its authentication flag. Only the [documented authentication-specific WS codes](https://www.okx.com/docs-v5/en/#error-code-websocket-public-general-class) without subscription identity are recognized during authentication; ambiguous generic request/subscription errors are not attributed by message text.

Verification: the original seven review cases and actual send/wait scenarios became permanent regressions; 10 initial acknowledgement cases and the two login cases failed before their fixes. All 55 new safety cases and all 699 offline tests pass; both netstandard targets build with zero warnings/errors. Coverage includes concurrent identical filters, ordered/reversed/duplicate ACKs, partial failure, missing/malformed identity, optional error fields, raw outcomes, request immutability/root ID serialization, repeated subscription attempts, completed/timed-out late callbacks, multi-argument unsubscribe, authentication codes, and unchanged generic channel routing. An older orders-unsubscribe fixture now echoes the sent ID, as the current contract requires. No live orders, credentials from the environment, private network connections, or server-enforcement tests were used.

Boundaries: a timeout or partial failure does not prove that zero server-side subscriptions exist; failed local subscription cleanup and existing reconnect behavior remain SDK-owned. No compensating unsubscribe, new automatic reconnect/resubscription, or trading retry was added. For non-orders ID-less unsubscribe, concurrent identical filters cannot be distinguished by ID; do not claim otherwise. Reconcile uncertain trading/subscription state deliberately. Package metadata remains 5.6.820; this is an unreleased follow-up to be included in the next dated release, not proof that any previously built/installed package contains these fixes. This development turn starts the new review interval; August 26 is next, with the final checkpoint still required after the remaining dated steps.
